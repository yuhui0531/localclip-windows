# Syntax highlighting diagnosis

用户报告：语法没高亮。

- [x] 检查卡片、详情、富文本和文件预览链路，以及 macOS 只读参考实现。
- [x] 复现长代码：0.1.6 的 TextPreview 在超过 16,384 UTF-16 单元后直接返回完整纯文本，导致已有高亮完全关闭。新增测试在修复前失败。
- [x] 确认 HTML 分支：编辑器同时提供 HTML 与正文时，详情无条件选择富文本 iframe，跳过正文识别。
- [x] 对比原有边界：短片段 relevance < 3 不识别是既有 macOS 兼容规则；卡片使用 180 字符摘要，用户已确认发生在历史卡片，语言和示例未提供，不能认定全部症状已解释。
- [x] 自检：问题属于渲染分支逻辑；不改拖动、输出、存储、OCR 或杀毒配置。无需改变用户的功能要求。

修复：详情用有界前缀生成高亮范围，再追加由 React 转义的完整尾部。防止 UTF-16 代理对在分界处被拆开，缓存仅保留有界前缀。已识别为代码的 HTML+文本条目使用统一代码显示；普通富文本仍使用原来的隔离 iframe。着色预算保持 16,384 单元，超出部分保持可读正文，不承诺全文着色。

验证：15 项代码/渲染回归通过；11 项 Chromium 布局测试通过，包含实际颜色、完整正文相等、富文本保留、图片缩放与拖动画布。原生验证与安装已完成（见 verification.md），原生验收使用生成的注释开头长代码；用户具体代码样本未提供。

用户确认卡片后，追踪到 core/store 只生成 180 字符摘要，普通搜索上下文也直接复用摘要；卡片将它当成完整语法识别输入。新增可见文本卡片的 previewOnly 读取，在现有隐私、删除复查后返回最多 16,384 个字符。UI 普通浏览改用此正文；搜索定位摘要保持原行为。新增浏览器用例覆盖只有注释的 180 字摘要后存在代码，验证颜色和原文；新增 Windows 单元测试覆盖读取边界且载荷不变。

最终原生验证：10 项通过，隐藏/恢复通过，实际查看了生成历史的卡片着色截图。测试驱动最初以字符串写入中文 CF_HTML 被拒绝为 unsupported；改用显式 UTF-8 字节后，同一二进制通过，保留该测试准备失败记录。0.1.7 ARM64 安装成功，6 个个人数据文件备份和升级前后哈希一致，正常用户启动后保护仍开启。
